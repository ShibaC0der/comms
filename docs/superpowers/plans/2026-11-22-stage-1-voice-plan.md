# Comms — этап 1: план реализации голоса

**Дата:** 2026-11-22  
**Статус:** одобрен; шаг 1 — каркас подготовлен, сборка ожидает проверки  
**Основание:** `../specs/2026-11-22-stage-1-voice-design.md`

## Правила работы

- Делаем по одному небольшому изменению и проверяем до перехода к следующему.
- Сначала работоспособная цепочка сигналинг → WebRTC → звук; не добавляем функционал из этапов 2–6.
- У задач есть конкретный проверяемый результат. Кодовые сниппеты и объяснения React-хуков — только по мере достижения соответствующей задачи.
- Версии зависимостей фиксируем при создании проекта: JDK 25 требует Gradle 9.1+; совместимость Kotlin Gradle Plugin и Ktor проверяем отдельно и не выбираем версии наугад.

## Шаг 1. Каркас проекта

**Сделать:** создать `backend/` (Ktor, Kotlin, Gradle Wrapper) и `frontend/` (Vite, React, TypeScript), `.gitignore`, краткий README со способом запуска. Сервер отвечает `GET /health` → `200 OK`; frontend показывает заголовок Comms. Настроить dev proxy `/ws` на backend.

**Зачем:** проверить инструменты и разделить проблемы сборки от проблем WebRTC.

**Подводные камни:** совместимость JDK/Gradle/Kotlin; конфликт портов; WebSocket proxy upgrade в Vite.

**Проверить:** `./gradlew test` и запуск сервера; `npm run build` и запуск dev-server; health endpoint отвечает, UI загружается.

**Стоп после шага:** показать результат запуска/логи, затем только следующий шаг.

## Шаг 2. WebSocket-протокол и registry

**Сделать:** `/ws`; выдача `selfId`, `welcome`, `peer-joined`, `peer-left`; маршрутизация `signal` с серверным `from`; registry с корректной синхронизацией. Добавить unit tests для добавления/удаления peers и запрета отправки несуществующему peer.

**Зачем:** WebRTC легче отлаживать, если протокол независимо проверен.

**Подводные камни:** гонки join/leave, одновременные подключения, send под mutex, spoofing `from`, отмена coroutine при закрытии WS.

**Проверить:** подключиться 2–3 WebSocket-клиентами через браузер или тест; вывести ID; закрыть одного; убедиться, что остальные получают `peer-left` и registry очищается.

## Шаг 3. Захват микрофона и минимальный UI

**Сделать:** кнопки «Подключиться»/«Отключиться», состояния `idle / connecting / connected / error`, `getUserMedia({ audio: true })`, локальный stream и `stop()` при выходе. Добавить `VoiceClient` и связать его с UI через `useRef`, `useState`, `useEffect`.

**Зачем:** локально проверить разрешения и жизненный цикл ресурсов до peer connections.

**Подводные камни:** React Strict Mode и cleanup; отказ доступа; устройство занято; повторный click; микрофон не выключается после выхода.

**Проверить:** разрешить/запретить доступ, подключиться и выйти несколько раз, убедиться в прекращении захвата и отсутствии дублирующих WebSockets.

## Шаг 4. WebRTC: два участника

**Сделать:** для второго участника создать PC; новичок отправляет offer, старый участник отвечает answer; добавлять один локальный audio track; пересылать trickle ICE, буферизовать кандидаты до remote description; выводить удалённый audio stream.

**Зачем:** получить первый настоящий звук.

**Подводные камни:** асинхронный порядок `setLocalDescription`/`setRemoteDescription`, ранние ICE-кандидаты, `ontrack`, блокировка autoplay, обратная акустическая связь.

**Проверить:** открыть две вкладки на `localhost` в наушниках, получить звук в обе стороны; увидеть `connected` для каждого PC; отсутствие ошибок в консоли и журнале signaling.

## Шаг 5. Три вкладки и корректная очистка

**Сделать:** `Map<peerId, PC>`; каждому существующему peer отправлять отдельный offer при входе нового; удалить PC/audio по `peer-left`; корректный `disconnect()` закрывает WS, PCs, tracks, события. Обработка сигнала от уже вышедшего peer без исключения.

**Зачем:** доказать full mesh, а не только одиночную пару.

**Подводные камни:** одна и та же дорожка микрофона должна переиспользоваться, а не захватываться заново на каждого собеседника; гонки выхода во время обмена SDP.

**Проверить:** три вкладки (3 пары PC), каждый слышит двух других; закрыть среднюю вкладку — оставшаяся пара не прерывается; поочерёдно входить/выходить повторно.

## Шаг 6. Минимальная диагностика и завершение этапа

**Сделать:** индикаторы WS и ICE/PC state, полезные ошибки; простой ручной test checklist в README; отладочные логи без SDP и приватных секретов. Прогнать backend tests, frontend build.

**Зачем:** облегчить обязательную сетевую отладку на этапе 2.

**Проверить:** весь чеклист из дизайн-спеки, включая denied mic и blocked autoplay. Зафиксировать ограничения и не добавлять пока комнаты или TURN.

## Короткий чеклист приёмки

- [ ] Backend и frontend запускаются из чистого checkout.
- [ ] Две вкладки обмениваются звуком.
- [ ] Третья вкладка подключается без перезапуска остальных.
- [ ] Выход одного участника не рвёт остальных.
- [ ] После выхода не остаются захваченные локальные tracks и PC.
- [ ] Ошибки разрешения микрофона/звуковоспроизведения видны в UI.
- [ ] Backend tests и TypeScript build проходят.

## Что точно не делать на этом этапе

Не подключать базу данных, TURN/STUN, комнатные ссылки, имена, админ-ключи, звуки событий, громкость по собеседнику, Redux, стейт-машины, универсальный event bus, reconnect и ICE restart. Идём к сетевому тесту как можно раньше.

## Переход к этапу 2

После приёмки этапа 1 готовим отдельную спецификацию на деплой, котурн и сетевые эксперименты. Обязательные сценарии: соединение между участниками в разных сетях; домашний и мобильный интернет; принудительный relay; соединение в браузере поверх работающей игры; оценка RTT, jitter, packet loss и субъективного качества звука.
