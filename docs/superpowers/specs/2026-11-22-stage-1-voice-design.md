# Comms — этап 1: голос в двух и более вкладках

**Дата:** 2026-11-22  
**Статус:** одобрен  
**Следующий документ:** `../plans/2026-11-22-stage-1-voice-plan.md`

## Контекст и цель

Сделать минимальное браузерное приложение, в котором 2–3 вкладки на `localhost` соединяются по WebRTC и слышат аудио друг друга. Backend на Kotlin/Ktor используется только для обмена сигнальными сообщениями по WebSocket; RTP-аудио через backend не проходит.

Этот этап подтверждает, что мы умеем организовать full-mesh и управлять жизненным циклом соединений. **Он не проверяет** соединение через NAT и надёжность в реальной сети: это проверяется на этапе 2.

## Границы этапа

**Входит:**

- `backend/`: Ktor, один WebSocket-маршрут `/ws`, одна неименованная комната в памяти.
- `frontend/`: Vite, React, TypeScript; единственная страница с кнопками «Подключиться»/«Отключиться», статусом, количеством собеседников и ошибкой микрофона.
- Захват одного локального аудиопотока `getUserMedia({ audio: true })` на вкладку.
- Отдельный `RTCPeerConnection` для каждого удалённого участника; тот же локальный трек добавляется во все peer connections.
- Offer/answer, trickle ICE, прослушивание входящих `MediaStream`, закрытие ресурсов при выходе.
- Минимальное логирование событий сигналинга и состояний соединений без записи SDP или содержимого аудио.
- Сценарии проверки для двух и трёх вкладок.

**Не входит:** STUN/TURN, HTTPS, домен, VPS, БД, комнаты по ссылке, имена, админ, регулировка громкости, speaking indicator, звуки входа, сложная переподключаемость, обработка ICE restart.

## Архитектура

```text
Вкладка A                                  Вкладка B
React UI                                  React UI
  |                                         |
VoiceClient                               VoiceClient
  |  \                                     /  |
  |   \--- WebSocket (signal only) -------/   |
  |                 |                       |
  |            Ktor /ws                    |
  |           in-memory registry           |
  |                                         |
  +========== WebRTC audio ===============+
           (на localhost, без TURN)
```

Сервер хранит подключённые WebSocket-сессии в registry `{peerId -> session}`. Он отвечает за выдачу ID и адресную доставку сигналов, но не создаёт peer connections, не преобразует SDP и не обрабатывает аудио.

**Конкурентный доступ:** операции над registry атомарны (например, через `Mutex`); сетевые `send` не удерживают общий mutex. При подключении выдаём новому участнику снимок уже зарегистрированных peers; это обеспечивает однозначное правило инициатора.

## Протокол сигналинга v1

Все сообщения — JSON-объекты с полем `type`. Названия полей условны до реализации, но семантика фиксируется.

| Направление | Тип | Поля | Смысл |
|---|---|---|---|
| клиент → сервер | `join` | `displayName` | Зарегистрироваться в комнате с указанным именем |
| сервер → новый участник | `welcome` | `selfId`, `displayName`, `peers: {peerId, displayName}[]` | Сервер выдал ID и перечень текущих участников |
| сервер → остальные | `peer-joined` | `peerId`, `displayName` | Новый участник появился; существующие **не** инициируют offer |
| клиент → сервер | `rename` | `displayName` | Изменить имя своей сессии |
| сервер → все участники | `peer-renamed` | `peerId`, `displayName` | Подтвердить новое имя участника |
| сервер → отправитель | `error` | `message` | Сообщить причину отказа в регистрации или смене имени |
| клиент → сервер | `signal` | `to`, `data` | Отправить SDP или ICE кандидата указанному peer |
| сервер → клиент | `signal` | `from`, `data` | Сервер доставляет сообщение, подставляя `from` из WebSocket-сессии |
| сервер → остальные | `peer-left` | `peerId` | Участник отключился, его PC нужно закрыть |

Форма `data`:

```ts
type SignalData =
  | { type: 'description'; description: RTCSessionDescriptionInit }
  | { type: 'candidate'; candidate: RTCIceCandidateInit };
```

Проверки сервера: клиент не может задавать `from`; `to` обязан существовать и отличаться от отправителя; JSON и размер сообщения ограничены; некорректные сообщения не приводят к падению других WebSocket-сессий.

### Правило инициирования соединения

**Только новый участник создаёт offer каждому ID из `welcome.peers`.** Уже подключённые участники ждут offer. Для каждой пары есть ровно один инициатор; так на этапе 1 исключаем одновременные offer (glare), не внедряя пока perfect negotiation.

Порядок на новой вкладке:

1. По явному нажатию «Подключиться» запросить микрофон. При отказе не открывать WebSocket и показать сообщение.
2. После получения `MediaStream` открыть `/ws` и отправить `join`. При успешной регистрации сервер присылает `welcome`.
3. Создать `RTCPeerConnection` для каждого уже присутствующего peer, добавить **тот же** локальный аудиотрек, отправить offer после `setLocalDescription()`.
4. Existing peer, получив `description: offer`, создаёт PC, добавляет свой локальный трек, делает `setRemoteDescription()`, затем answer и `setLocalDescription()`, отправляет answer.
5. Каждая сторона пересылает ICE-кандидаты через сервер. Если кандидат пришёл до `setRemoteDescription()`, временно положить его в очередь для этого peer и применить после remote description.
6. При `ontrack` присоединить удалённый поток к отдельному `HTMLAudioElement`, попытаться `play()`; если autoplay заблокирован, показать понятную кнопку «Включить звук».
7. При `peer-left` закрыть PC и убрать audio element. При собственном отключении закрыть WebSocket, все PCs, остановить все локальные tracks и очистить обработчики.

**Одновременные подключения:** сервер атомарно формирует снимок участников и добавляет нового; у двух новых вкладок одна из них будет в снимке другой. Доставка `signal` должна работать независимо от того, пришёл ли `peer-joined`.

**Ограничение этапа:** renegotiation и ICE restart не реализуются, так как все audio tracks добавлены до первого offer. На этапе 6 при необходимости перейдём на perfect negotiation.

## Frontend: разделение ответственности

Минимальное разделение:

- `VoiceClient` (обычный TypeScript, не React): WebSocket, `Map<peerId, RTCPeerConnection>`, локальный stream, удалённые streams, offer/answer/ICE, `connect()`/`disconnect()` и события для UI.
- `App.tsx` (React): кнопки, статусы, отображение участников и ошибок; владеет экземпляром `VoiceClient`.

Для обучения React важно различать:

- `useState` — видимое состояние UI (`idle`, `connecting`, `connected`, `error`; список peer ID).
- `useRef` — сохраняемый между рендерами экземпляр `VoiceClient` или другое mutable значение, которое не должно запускать рендер.
- `useEffect` — подписка на события клиента и cleanup при размонтировании; подключение запускается нажатием кнопки, **не** автоматически из эффекта. Это также предотвращает неожиданный второй коннект при повторной проверке эффектов в React Strict Mode.

Vite проксирует `/ws` на Ktor в development, чтобы клиент использовал относительный URL и не усложнял этап CORS-политиками.

## Пограничные случаи

- Вторая вкладка открылась во время переговоров первой пары — registry и адресная доставка работают корректно.
- Участник закрывает вкладку до завершения SDP/ICE — остальные получают `peer-left`, а задержанные сигналы игнорируются без ошибки в UI.
- Пользователь отказал микрофону — не появляется «пустой» peer в комнате.
- Вызов `HTMLMediaElement.play()` отклонён политикой autoplay — доступна ручная активация.
- Один и тот же браузер воспроизводит звук на микрофон этой же машины — для проверки нужны наушники/раздельные устройства, иначе возникает акустическая обратная связь.
- `localhost` допустим для `getUserMedia` без HTTPS; на удалённом хосте этапе 2 потребуется HTTPS.

## Диагностика и критерии готовности

Обязательные наблюдаемые данные: статус WS, `connectionState` / `iceConnectionState` каждого PC, количество peers, ошибка `getUserMedia` или `play`. В Chrome удобно дополнительно проверить `chrome://webrtc-internals`.

**Готово, когда:**

1. Один сервер и frontend запускаются локально документированными командами.
2. Две вкладки по явному нажатию подключаются и передают двусторонний звук.
3. Третья вкладка слышит обе другие и слышна им; не появляются дублирующиеся соединения.
4. После закрытия одной вкладки два остальных подключения остаются живыми.
5. Повторное подключение после отключения не требует обновления страницы и не оставляет активного микрофона/PC после выхода.
6. Отказ микрофона, потеря WebSocket и autoplay-blocking не приводят к зависанию интерфейса или необработанным исключениям.
7. Backend tests на поведение registry/адресацию пройдены; frontend собирается без ошибок TypeScript.

## Отложенные решения

- Этап 2: STUN + coturn, TURN credentials, `iceTransportPolicy: 'relay'` для диагностики.
- Этап 2: нельзя без дополнительной схемы одновременно слушать Caddy HTTPS и coturn TURNS на TCP 443 на одном IP; выбрать отдельный IP или L4 TLS/SNI-мультиплексирование. Также открыть UDP relay-порты coturn.
- Этап 3: persistent room ID, имена, максимум участников.
- Этап 6: reconnect identity, ICE restart, таймаут присутствия и perfect negotiation при необходимости.
